1-1. LLM의 환각

**환각 Hallucination**

`LLM이 알지 못하는 내용을 사실처럼 자연스럽게 만들어내는 현상`

LLM에게 학습하지 않은 회사의 내부 규정을 질문하면 정확한 근거 없이 답을 생성할 수 있다.

```python
question = "무지개상사의 리모트 근무 정책은 무엇인가요?"

messages = [
    {
        "role": "user",
        "content": f"""
다음 질문에 한국어로 간단히 답하세요.

질문: {question}
"""
    }
]

result = generator(
    messages,
    max_new_tokens=100,
    do_sample=False
)

answer = result[0]["generated_text"][-1]["content"]

print(answer)
```

```plain text
LLM이 회사 내부 문서를 모름
→ 하지만 다음에 올 가능성이 높은 문장을 생성
→ 그럴듯하지만 틀린 답변이 나올 수 있음
```

1-2. RAG

**RAG Retrieval-Augmented Generation**

`질문과 관련된 문서를 먼저 검색한 뒤, 검색 결과를 참고 자료로 제공해 답변을 생성하는 방식`

```plain text
질문
→ 관련 문서 검색 Retrieval
→ 프롬프트에 문서 추가 Augmentation
→ 문서를 근거로 답변 생성 Generation
```

RAG는 LLM에게 새로운 지식을 다시 학습시키는 것이 아니라 답변할 때 참고할 자료를 제공한다.

```plain text
순수 LLM
→ 기억에 의존하는 시험

RAG
→ 관련 자료를 찾아보는 오픈북 시험
```

2-2. 단어 겹침 검색

가장 단순한 검색 방법은 질문과 문서에 겹치는 단어의 개수를 계산하는 것이다.

```python
def word_overlap_search(question, documents):
    question_words = set(question.split())

    best_doc = None
    best_score = -1

    for doc in documents:
        doc_words = set(doc.split())

        score = len(
            question_words & doc_words
        )

        if score > best_score:
            best_score = score
            best_doc = doc

    return best_doc
```

```python
question = "무지개상사의 리모트 근무 정책은 무엇인가요?"

retrieved_doc = word_overlap_search(
    question,
    documents
)

print(retrieved_doc)
```

```plain text
질문 단어 집합
∩
문서 단어 집합
→ 겹치는 단어 개수 계산
```


4-2. 검색 품질의 중요성

```plain text
좋은 문서 검색
→ 좋은 참고 자료
→ 정확한 답변 가능

잘못된 문서 검색
→ 잘못된 참고 자료
→ LLM도 잘못된 답변 생성
```

RAG의 성능은 생성 모델뿐 아니라 검색기의 품질에 크게 영향을 받는다.

5-2. 코사인 유사도

**코사인 유사도**

`두 벡터의 방향이 얼마나 비슷한지 나타내는 값`

```python
import numpy as np

def cosine_similarity(v1, v2):
    return np.dot(v1, v2) / (
        np.linalg.norm(v1)
        * np.linalg.norm(v2)
    )
```

```python
print(
    cosine_similarity(emb1, emb2)
)

print(
    cosine_similarity(emb1, emb3)
)
```

- `1`에 가까움 : 의미가 매우 비슷함
- `0`에 가까움 : 관련성이 낮음
- `1`에 가까움 : 방향이 반대
```plain text
강아지와 개
→ 글자는 다르지만 의미가 비슷함
→ 높은 코사인 유사도

강아지와 주식
→ 의미가 다름
→ 낮은 코사인 유사도
```

6-2. 가장 유사한 문서 찾기

```python
def embedding_search(
    question,
    documents,
    doc_embeddings,
    model
):
    question_embedding = model.encode(
        question
    )

    similarities = [
        cosine_similarity(
            question_embedding,
            doc_embedding
        )
        for doc_embedding in doc_embeddings
    ]

    best_idx = np.argmax(similarities)

    return (
        documents[best_idx],
        similarities[best_idx]
    )
```

```python
best_doc, score = embedding_search(
    "다 같이 모이는 시간이 언제야?",
    documents,
    doc_embeddings,
    embedding_model
)

print(best_doc)
print(score)
```

임베딩 검색은 단어가 정확히 일치하지 않아도 의미가 비슷한 문서를 찾을 수 있다.

```plain text
단어 검색
→ 글자가 같은가?

임베딩 검색
→ 의미가 비슷한가?
```

실무에서는 가장 유사한 문서 하나만 사용하는 것보다 상위 여러 문서를 함께 검색하는 경우가 많다.

```python
def top_k_search(
    question,
    documents,
    doc_embeddings,
    model,
    k=2
):
    q_emb = model.encode(question)

    similarities = [
        cosine_similarity(
            q_emb,
            doc_emb
        )
        for doc_emb in doc_embeddings
    ]

    top_indices = np.argsort(
        similarities
    )[-k:][::-1]

    return [
        (
            documents[idx],
            similarities[idx]
        )
        for idx in top_indices
    ]
```

```plain text
Top-1
→ 가장 유사한 문서 1개

Top-3
→ 상위 문서 3개

Top-K가 너무 작음
→ 필요한 정보가 제외될 수 있음

Top-K가 너무 큼
→ 관련 없는 정보가 프롬프트에 포함될 수 있음
```

9-2. FAISS

**FAISS**

`대량의 벡터에서 유사한 벡터를 빠르게 찾기 위한 라이브러리`

```python
import faiss
```

벡터를 먼저 정규화한다.

```python
large_norm = (
    large_embeddings
    / np.linalg.norm(
        large_embeddings,
        axis=1,
        keepdims=True
    )
)

query_norm = (
    query_vec
    / np.linalg.norm(query_vec)
)
```

FAISS 인덱스를 생성하고 벡터를 등록한다.

```python
dimension = 384

index = faiss.IndexFlatIP(
    dimension
)

index.add(
    large_norm
)
```

```python
similarities, indices = index.search(
    query_norm,
    k=1
)
```

- `IndexFlatIP` : 내적을 이용하는 인덱스
- `add()` : 벡터 등록
- `search()` : 가장 가까운 벡터 검색
- `k` : 반환할 문서 개수
9-3. 정규화와 내적

벡터 길이를 1로 정규화하면 두 벡터의 내적은 코사인 유사도와 같은 값이 된다.

```plain text
벡터 정규화
+
IndexFlatIP
→ 코사인 유사도 기반 검색
```

※ 문서와 질문을 동일한 방식으로 정규화해야 함

13-1. Chunking

**청킹 Chunking**

`긴 문서를 검색하기 적절한 크기의 작은 조각으로 나누는 과정`

```plain text
긴 문서 한 개
→ 여러 개의 작은 청크
→ 각 청크를 개별 임베딩
→ 질문과 관련된 청크만 검색
```

13-2. 고정 길이 청킹

```python
def fixed_length_chunking(
    text,
    chunk_size=80
):
    text = (
        text.strip()
        .replace("\n", " ")
    )

    return [
        text[i:i + chunk_size]
        for i in range(
            0,
            len(text),
            chunk_size
        )
    ]
```

```python
fixed_chunks = fixed_length_chunking(
    handbook_text,
    chunk_size=80
)
```

- 구현이 간단함
- 청크 크기가 일정함
- 문장 중간에서 잘릴 수 있음
```plain text
무지개상사는 2020년 3월 15일에 설립된 IT 스타
→ 문장 중간에서 잘림
→ 정보가 온전하게 남지 않을 수 있음
```

13-3. Overlap 청킹

**Overlap**

`이전 청크의 일부 내용을 다음 청크에 겹쳐 포함하는 방법`

```python
def overlapping_chunking(
    text,
    chunk_size=80,
    overlap=20
):
    text = (
        text.strip()
        .replace("\n", " ")
    )

    chunks = []
    start = 0

    while start < len(text):
        chunks.append(
            text[
                start:start + chunk_size
            ]
        )

        start += (
            chunk_size - overlap
        )

    return chunks
```

```plain text
청크 1
→ 0~79번째 글자

청크 2
→ 60~139번째 글자

60~79번째 글자
→ 두 청크에 모두 포함
```

경계에서 문장이 끊겨도 겹치는 부분 덕분에 어느 한 청크에는 정보가 온전히 포함될 가능성이 높아진다.

13-4. 문장 단위 청킹

```python
import re

def sentence_chunking(
    text,
    max_chars=150
):
    sentences = re.split(
        r"(?<=[.!?])\s+",
        text.strip().replace("\n", " ")
    )

    chunks = []
    current = ""

    for sentence in sentences:
        if (
            len(current)
            + len(sentence)
            <= max_chars
        ):
            current += (
                " " + sentence
            )
        else:
            chunks.append(
                current.strip()
            )

            current = sentence

    if current:
        chunks.append(
            current.strip()
        )

    return chunks
```

```python
    max_chars=150
```

16-1. RAG 함수

```python
def ask_mujibot(
    question,
    k=2
):
    # ① 검색
    q_emb = embedding_model.encode(
        [question],
        normalize_embeddings=True
    ).astype("float32")

    _, indices = mujibot_index.search(
        q_emb,
        k=k
    )

    retrieved = [
        handbook_chunks[idx]
        for idx in indices[0]
    ]

    # ② 증강
    context = "\n".join(
        retrieved
    )

    prompt = f"""
다음 참고 자료를 바탕으로 질문에 답하세요.

참고 자료:
{context}

질문:
{question}

답변:
"""

    # ③ 생성
    result = generator(
        prompt,
        max_new_tokens=120
    )

    answer = result[0][
        "generated_text"
    ]

    return answer, retrieved
```

16-3. 근거 문서 표시

RAG 서비스에서는 답변만 보여주는 것보다 참고한 원문도 함께 표시하는 것이 중요하다.

```plain text
답변
→ 사용자가 결과를 확인

근거 문서
→ 답변이 어디에서 나왔는지 검증
→ 서비스 신뢰도 향상
```

※ 검색된 청크가 실제 답변을 충분히 뒷받침하는지 확인해야 함

---

RAG는 검색기를 추가했다고 자동으로 정확해지는 것은 아니다.

대표적인 실패 원인

```plain text
문서 문제
→ 필요한 정보가 문서에 없음

청킹 문제
→ 정보가 경계에서 잘림

임베딩 문제
→ 질문과 문서의 의미를 잘 표현하지 못함

검색 문제
→ 올바른 청크가 Top-K 안에 들어오지 않음

프롬프트 문제
→ 참고 자료를 무시하고 답함

생성 문제
→ 근거에 없는 내용을 추가 생성
```

RAG 오류를 분석할 때는 먼저 검색 결과부터 확인해야 한다.

```plain text
1. 올바른 청크가 검색되었는가?
2. 검색된 청크에 정답이 존재하는가?
3. 프롬프트가 문서 기반 답변을 요구하는가?
4. 생성 모델이 참고 자료를 제대로 사용했는가?
```

## 💭 오늘의 회고

- **배운 점**
- 환각 : LLM이 근거 없는 내용을 사실처럼 생성하는 현상
- RAG : 외부 문서를 검색해 LLM의 답변 생성에 활용하는 방식
- RAG는 검색, 증강, 생성의 세 단계로 구성
- 검색된 문서는 LLM 프롬프트의 참고 자료로 추가
- RAG는 모델을 다시 학습시키지 않고 필요한 문맥을 제공
- 단어 겹침 검색은 같은 단어가 있을 때만 잘 동작
- 표현이 달라도 의미가 같을 수 있으므로 임베딩 검색이 필요
- 임베딩 : 문장 의미를 숫자 벡터로 표현
- 코사인 유사도 : 두 벡터의 방향이 얼마나 비슷한지 계산
- 의미가 비슷한 질문과 문서는 높은 유사도를 가질 수 있음
- Top-K 검색 : 가장 유사한 문서를 여러 개 가져오는 방식
- K가 너무 작으면 정답 문서를 놓칠 수 있음
- K가 너무 크면 관련 없는 문서가 프롬프트에 포함될 수 있음
- FAISS : 대량의 벡터에서 유사한 벡터를 빠르게 검색
- `IndexFlatIP` : 내적을 기준으로 검색하는 FAISS 인덱스
- 정규화된 벡터의 내적은 코사인 유사도와 같은 값
- 질문과 문서 벡터는 동일한 방식으로 정규화해야 함
- `index.add()` : 문서 벡터를 FAISS에 등록
- `index.search()` : 질문과 가까운 벡터 검색
- ChromaDB : 문서, ID와 임베딩을 함께 관리하는 벡터 데이터베이스
- 긴 문서를 하나의 벡터로 만들면 구체적인 정보가 희미해질 수 있음
- Chunking : 긴 문서를 검색 가능한 작은 단위로 나누는 과정
- 고정 길이 청킹은 간단하지만 문장이 중간에서 잘릴 수 있음
- Overlap은 청크 경계를 겹쳐 정보 손실을 줄임
- 문장 단위 청킹은 문장 중간이 끊기는 문제를 줄일 수 있음
- 청크가 너무 작으면 문맥이 부족하고 너무 크면 검색 결과가 뭉뚱그려짐
- 청크는 질문 하나에 답할 수 있을 정도의 문맥을 포함해야 함
- 사내 챗봇은 검색→증강→생성을 하나의 함수로 연결해 구현
- 답변과 함께 검색된 근거 문서를 제공하면 신뢰성을 높일 수 있음
- RAG 오류를 분석할 때는 생성 결과보다 검색 결과를 먼저 확인
- 문서에 정답이 없으면 모른다고 답하도록 프롬프트에 명시
- LangChain : RAG 구성 요소를 연결하는 프레임워크
- `RecursiveCharacterTextSplitter` : 문서를 큰 단위부터 재귀적으로 분할
- `HuggingFaceEmbeddings` : Hugging Face 임베딩 모델 연결
- `FAISS.from_texts()` : 문서 임베딩과 벡터 저장소 생성을 함께 처리
- `similarity_search()` : 질문과 유사한 문서 검색
- `HuggingFacePipeline` : Hugging Face 생성 모델을 LangChain에 연결
- `RetrievalQA` : 검색, 프롬프트 구성과 생성을 하나의 체인으로 실행
- 직접 구현은 내부 원리 이해와 세밀한 제어에 적합
- LangChain은 빠른 프로토타입과 구조 변경에 적합
- 좋은 RAG는 생성 모델뿐 아니라 문서 품질, 청킹, 임베딩과 검색 품질이 중요
